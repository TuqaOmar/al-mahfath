# Isolated Firebase verification

Run from the repository root on Windows:

```powershell
npm.cmd run test:security
npm.cmd run test:emulator
npm.cmd run test:emulator:browser
npm.cmd run test:emulator:browser -- --mobile-only
```

The runner uses `demo-ma7fath-test`, Auth at `127.0.0.1:9099`, Firestore at `127.0.0.1:8080`, and Storage at `127.0.0.1:9199` for browser runs. It copies the checked-in rules to a temporary configuration, creates disposable accounts with password sign-in, seeds synthetic documents, and verifies real rules and HTTP responses. JSON fixtures live in a temporary directory; hashes verify that repository databases stay unchanged. There is no deployment or production migration command.

Install Firebase CLI locally with `npm.cmd install --save-dev firebase-tools` when npm connectivity is available. Alternatively download the [official Windows standalone CLI](https://github.com/firebase/firebase-tools/releases) to `.tools/firebase.exe`. The runner can also use the CLI cache populated by the standalone tool. This session used CLI 15.32.1 and Firestore emulator 1.22.0.

Java 21 is required. Put a portable JDK under `.tools/java/jdk-21...` or make Java 21 available on PATH. This session used Temurin 21.0.12.1. The runner copies a local JDK and rules to Latin-character temporary paths because the Windows Java launcher failed with the Arabic repository path. Downloads and caches are ignored by Git. Network access is needed for the first emulator download; subsequent runs use the cached JAR.

The application server rejects any emulator configuration unless `NODE_ENV=test`, `MA7FATH_EMULATOR_TEST=1`, a `demo-*` project, and both loopback emulator hosts are present. The runner sets these variables for its child process, never in `.env` or production configuration. It verifies that production startup rejects emulator hosts. Outside tests, the server uses the same named database specified in `firebase-applet-config.json` as the frontend; `FIRESTORE_DATABASE_ID` is an explicit override.

`memberships/{uid}` currently holds one active membership per learner. Transfers replace this document, and leaving removes it; concurrent memberships and membership history are not represented. A server transaction updates this document, user membership pointers, group counts, and request approval together. This is a current implementation constraint, not an agreed final product requirement.

`enrollmentRequests/{uid}` currently holds one request document per learner, including after approval. A pending duplicate returns the previous request without changing its details. Submitting after approval (or any non-pending status) uses `tx.set` without merge and replaces the previous document, removing approval fields such as `approvedBy`, `approvedAt`, `groupId`, and `teacherId`. Request history is not preserved. Transaction test success does not endorse this constraint as a final requirement; multiple memberships and request history need a product decision before moving legacy data.

Direct client writes to groups, memberships, requests, and user membership pointers are denied. Teacher assignment uses existing registered Firebase accounts. Existing JSON memberships are not migrated or silently imported. To reproduce the local-only legacy inventory without accessing Firebase, run `node scripts/auditLegacyMemberships.mjs --output reports/legacy-memberships.md`; the [redacted report](../reports/legacy-memberships.md) distinguishes primary files from backups and is not a production Firestore/Auth inventory.

API coverage includes role escalation and system field rejection, allowed profile edits, student progress isolation, real ID tokens for four roles, teacher scope and revocation, group creation/join/transfer/leave, approval retry, concurrent joins, and an injected transaction failure returning 503 without modifying membership.

The browser command runs installed Google Chrome headless through Playwright, with disposable contexts (no personal Chrome profile), the real React UI served in Vite `emulator` mode, and the same demo Auth/Firestore/Storage services. It assigns teacher roles, creates two groups, checks the displayed invitation code and clipboard copy, joins from the student dashboard, verifies membership and teacher rosters after reload, transfers the learner between teachers, logs out/in, leaves, approves a seeded pending request, and signs in as its owner to verify approved membership after reload. It then submits a synthetic text-practice attempt, proves retry idempotency and zero-value rendering in the teacher/admin screens, injects report/save failures, retries, and verifies persistence after a fresh sign-in. Another journey switches a multi-role account among student, teacher, and admin surfaces, checks API authorization, exercises a Firestore post through create/read/edit/delete plus like/comment notifications and cross-user denial, and uploads a profile PNG through Storage before checking reload and fresh sign-in. An oversized image verifies the failure message and retention of the previous photo. The seventh journey saves a student's manual learning plan and one self-recorded ayah status, verifies both after logout/sign-in and on the assigned teacher and admin screens, and proves that XP and verified memorized-page counts do not change. Assertions accompany screenshots and `result.json` in `reports/browser-groups/`. External browser traffic is blocked; repository JSON hashes must stay unchanged.

The optional `--mobile-only` browser run selects the emulator safety checks plus the mobile responsive journey. It verifies student, teacher, admin, and multi-role section navigation at 320, 360, 390, and 430 CSS-pixel widths, checks theme persistence after reload, and saves Chrome screenshots under `reports/mobile-responsive/`.

The recitation journey proves that the server ignores client Quran text and uses the bundled `quran-uthmani` corpus after validating the surah, global ayah, and page. The interactive Mushaf fetches page 2 from that same local endpoint. Chrome compares every displayed ayah with the endpoint byte-for-byte, checks fatha, damma, kasra, sukun, shadda, and tanween, and verifies RTL plus a Naskh-capable font stack. The recitation response returns the exact `referenceText`; the test sends a forged client reference and proves that the server-used text still equals the visible ayah. The learner submits a saved practice session, the assigned teacher reviews it, saves a note, and sees live report totals; the learner sees the note after a fresh sign-in. API coverage exercises approval and rejection and denies an unrelated learner and teacher. Neither decision changes XP, portfolio progress, or verified memorized pages. Microphone capture, ASR/Gemini, audio formats, tajweed quality, and visual comparison with an independently printed Mushaf remain outside this browser evidence. The older `QuranSurahAyahsModal` now uses the same endpoint but is not connected to a current UI path, so it is not claimed as browser-tested.

The eighth browser journey opens the administration UI, persists Community and achievements visibility/order plus badge display metadata in `app_config/navigation`, and verifies the resulting student navigation and badge cards after refresh. It hides Community and one badge, edits another badge title, and proves that an existing `users/{uid}.earnedBadges` value is unchanged. A direct Firestore REST write with the learner token must return 403; authenticated users may read the configuration, while only an administrator may create or update it. This configuration changes presentation only: it does not add badge types, alter award criteria, or revoke previously earned badges.

The profile-photo checks upload a PNG through the Storage emulator, wait for the Firestore profile write, and verify the URL in the sidebar after refresh and a fresh sign-in. They also reject an oversized file, force the profile write to fail after a new Storage upload and verify cleanup/retention of the previous picture, and use the Storage REST API to prove that a learner cannot upload under another user's avatar directory. The ninth browser journey verifies two group counts against active `memberships` documents after join, transfer, leave, and approval. API coverage additionally overwrites the cached group counters with 999 and 777 and proves the returned counts still come from active membership records, excluding an inactive fixture and avoiding duplicate concurrent joins.

Administration activity metrics are tested first with no activity records, where every available metric renders zero. Known Emulator records then prove one user active today, two active in the trailing seven Amman calendar days, one recent registration, one recent active membership, one reviewing teacher, one group with a recently active learner, and two recitation sessions in the trailing 30 days. Weekly activity uses `users.lastQuranActivityDate`; registrations use `users.createdAt`; current joins use active `memberships.updatedAt`; teacher reviews use session `reviewedAt/reviewedBy`; recitation totals use session `createdAt`. The dashboard shows “unavailable” for weekly-plan completion because no unified source exists.

`users/{uid}.streak` counts consecutive Amman calendar dates with a newly committed recitation attempt. Authentication, reload, membership changes, and retrying an existing session ID do not count. The session and streak update share one Firestore transaction. The tests cover no-activity sign-in, the first qualifying activity, a second activity on the same date, a persisted previous-day state followed by today's activity, and a fresh browser sign-in. Client writes to `streak` and `lastQuranActivityDate` remain denied. Existing profiles without `lastQuranActivityDate` begin a documented streak at one on their next qualifying activity.

The frontend switch is set only in the child process: `VITE_MA7FATH_EMULATOR=1`. It requires development mode named `emulator` and a loopback page hostname, and selects a demo config with the default database. Production builds and ordinary development reject this switch; the safety tests exercise both. Do not put the switch or emulator hosts in production configuration.

Chrome must be installed at its standard location; `@playwright/test` is a dev dependency. A pending request is seeded as a fixture: the browser test proves approval, not a request-submission screen. Quran page display and comparison both use the bundled server corpus; this does not test speech recognition, tajweed, audio, or memorization. Wizard, mobile/native builds, production credentials, and deployment remain outside this evidence.

The tenth browser journey opens the student's analytics after refresh and verifies one self-declared ayah, one practice attempt at 80%, and unavailable approved memorized pages as separate measures. It opens a teacher dashboard with two groups containing one and zero active members, then proves another teacher with no active members sees zero sessions and an unavailable activity ratio. API coverage uses isolated teachers and students to verify the same scope, an empty student dataset, inactive-membership exclusion, and cross-teacher denial. The seven-day window uses stored recitation createdAt values and Amman date labels; practice and teacher review decisions are never labeled approved memorization.


Teacher scope regression (2026-10-05): canonical membership uid/status/group/teacher and CURRENT group ownership govern student/profile/progress/history, notes/review and teacher aggregates, including direct Firestore reads. Former teachers retain no history exception. Available students are current active assigned students; unassigned enrollment uses self-join or administration. A transferred pending practice requires student resubmission before the new teacher can review it. Admin broad reads remain; decisions/notes require the actual assigned teacher. Synthetic malformed/inactive, nested-path, transfer, leave, stale-pointer, group-specific UI, failed-read clearing and delayed-note-response regressions are included. Views refresh on mount/focus/manual request and visible-tab30-second polling; instant push invalidation/offline timing is not tested. The runner isolates Firebase CLI configuration in its temporary directory and deletes that directory after completion. PROJECT_STATUS.md records the actual final command results and limits.

False-persistence regressions (2026-10-05): fortress plans use the owner-authenticated GET/POST `/api/user/fortress-plan` routes and `users/{uid}/five_fortresses_plans/current`. The server transaction writes the plan and numeric `preferences.fortressesToday` projection together, using the Amman completion date, without XP, activity streaks, memorization approval or earned awards. Direct client plan writes are denied. A missing plan is an unsaved generated draft; failed reads never fall back to localStorage or write a daily reset. AI chat suggestions become plan text only through the explicit save button. The quiz and fortress preference customizer each use one authenticated PUT `/api/user/{uid}`, merging preference patches transactionally and requiring `success:true,persisted:true` plus the committed owner profile. Quiz percentages are the weighted answers, not measured proficiency.

The API regressions inject a failed Firestore transaction and compare both old documents before retry, verify one current plan, token ownership, rules denial, and fresh Auth sign-in reads. Chrome navigates to the quiz from Home → **تعديل الخطة**, uses every fortress view and all five home completion controls, tests 503 and HTTP200/success:false, stale local cache/read failure, retry, refresh and logout/login, and compares Firestore snapshots and unchanged rewards. Dashboard refresh confirms only a fresh authenticated profile read. A missing synthetic profile exercises real Firestore refresh failure; it is restored in `finally`. Mobile pull uses DOM touch events in Chrome with a mobile viewport, not a physical phone. Reminder completion now only dismisses a local reminder and never claims a persisted session. The standalone fortress setup wizard has no current UI caller and is not browser-tested. Live Gemini, Push, complete offline/reconnection and native-device behavior remain outside these regressions. See PROJECT_STATUS.md and `reports/browser-groups/result.json` for actual run results.
